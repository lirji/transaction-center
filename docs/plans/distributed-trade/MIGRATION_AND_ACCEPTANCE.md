# 分布式演进阶段、迁移与验收

日期：2026-09-09。状态：待审查设计，不是执行记录。参照[边界设计](../../DISTRIBUTED_SERVICE_DESIGN.md)与[协议草案](../../DISTRIBUTED_PROTOCOLS.md)。本稿没有运行多实例、故障注入或压力测试，历史451项后端/49项前端测试不证明下列场景通过。

## 1. 分阶段实施

| 阶段 | 交付物 | 放行条件 |
| --- | --- | --- |
| P0：现有多实例基线 | 隔离数据库、两个API、至少两个Worker实例、故障脚本及报告 | 真正不同进程的并发/接管/旧实例恢复；不触碰演示库和共享渠道业务 |
| P1：普通查询与消费者 | 逐页面字段的事件/权威查询完整性清单、增量/全量回填、查询投影和滞后提示 | 新老查询数据核对；没有跨库写；普通查询与强证据接口分流 |
| P2：库存提取 | 组预占、确认/取消、回库协议；订单协调状态 | 库存/关闭/回库矩阵全通过；收款—库存—首单确认点及零元/回库API语义变更审查完成；正常付款/首单事件及资格证据消费者签收，WAIT_STOCK准入线性化与冻结/下架交错规则明确 |
| P3：资金提取 | 订单绑定、许可/关闭屏障、退款双预算、资金首付事实 | 新证据/首单策略合同及消费者签收，可靠渠道关闭合同，完整恢复演练 |
| P4：其余域独立 | 会员/商品准入许可与撤销、独立履约等 | 冻结/下架线性化语义和跨服务访问权验证；收益有实测依据 |

阶段可以停止在任意已验收边界。若P3证据或渠道屏障未满足，则继续同库部署，不把“最终一致”作为放宽业务不变量的理由。

## 2. P0隔离验证计划

复用现有镜像/依赖版本，但故障注入使用项目专属隔离实例与数据。公共中间件优先dev_infra；需要退出、断网、磁盘故障等破坏性实验时，建立明确测试用途的隔离组件，不向共享实例注入故障。演示4180/8400服务保持正常。

测试角色至少包括API-A/API-B、Worker-A/Worker-B和隔离MySQL。支付渠道使用显式测试适配器，能控制“接收请求但响应丢失”“关闭后旧CREATE到达”等行为；不接生产渠道。测试身份/密钥仅属于隔离环境，不输出凭据。

首先记录环境、提交和差异、资源限制、实例数、池大小、线程与租约配置、种子分布；通过SQL/业务种子写入库，不在页面写硬编码数据。先低并发正确性，再阶梯负载，最后故障恢复；目标RPS、P99和恢复SLO须在执行计划中明确后才可宣称达标。

## 3. 数据迁移和唯一写入方切换

1. **盘点**：按48表归属核对每个写入口、跨域外键、唯一键、任务及审计、永久幂等/归因记录、密文密钥版本、消费者。每项登记唯一所有者，不能只迁业务主表。
2. **先扩协议**：在旧核心内实现与测试新命令/状态协议，保留原数据库事务适配器；用特性开关逐步接入，外部消费者先能理解新版本。
3. **准备目标库**：新迁移单独评审、表/字段注释齐全，账号最小权限。建立绑定/唯一键/恢复表，密文迁移保留原keyVersion及获准的历史解密能力。
4. **快照与增量**：采用一致性快照+提交日志水位或受控停写快照。增量有去重和断点；自增ID上界不是提交水位，不能漏掉迟提交的小ID。回填事件不触发支付/发奖/回库等副作用。
5. **核对**：租户级数量、主键/绑定、金额与数量守恒、永久请求与终止标记、待处理任务、事件游标都要核对。允许滞后的投影先追平到明确水位；不以总行数相同代替资金核对。
6. **切写**：一期优先受控停写窗口。停旧API相关写入口，停旧Worker并确认全部在途事务和渠道计划归属；追平最后水位，撤销旧写权限，再将命令路由切到新所有者。所有订单支付尝试必须只进入同一资金权威，不能随请求随机路由到新旧两个库。
7. **恢复**：从新所有者恢复任务与发布，继承原业务号、eventId、渠道号、命令摘要、关闭标记及租约代际。旧实例不能靠尚持有的凭据继续写；本地token迁移要确保陈旧进程不能完成任务。
8. **观察**：比对增量资金/库存守恒、未知状态、投影延迟、消费缺口和服务错误。达到阶段门禁后才能解除旧资源保留。

严禁应用层无事务双写两个业务库来“保持同步”。CDC只作迁移/投影工具，不形成两个业务裁决者。跨域外键在替代校验及孤立数据核对通过后按独立迁移处理，不能修改已执行V001–V033。

## 4. 回退策略

- 新库尚未接写：可撤销路由变更，保留原权威；目标影子数据不能反向覆盖原库。
- 新库已接写：不能直接把流量切回旧快照。应暂停相关新增命令，继续保留资金证据接收/可靠缓冲，恢复新服务或在隔离条件下完成反向迁移、追平与权限切换；同样只能有一个写入者。
- 外部资金操作已发生：不能通过恢复数据库备份抹掉该事实；需渠道对账与恢复。回退应用版本也不能重新开放旧支付创建路径或删除关闭屏障。
- 业务中间状态、永久幂等记录和新事件版本存在后，旧代码未必兼容；回退版本必须经过协议兼容验证，不做未经验证的滚动混跑。

## 5. 必测矩阵与判定

| 编号 | 场景 | 不可放宽的断言 |
| --- | --- | --- |
| D-01 | 两API同号同内容/异内容竞争 | 同内容一个永久业务结果；异内容冲突 |
| D-02 | 多SKU仅一项库存不足 | 没有半组预占；订单有确定失败或待恢复状态 |
| D-03 | Reserve响应丢失，Cancel先到，迟到Reserve | 终止标记阻止重新预占；同组不重复释放 |
| D-04 | Confirm重复及与Cancel竞争 | 确认不重复扣；已确认不能普通释放；矛盾依据进入核对 |
| D-05 | 无意图先Close，后到Open | 永久订单关闭屏障阻止创建任何新attempt |
| D-06 | 旧Worker暂停在渠道调用前，另一实例关闭后恢复旧CREATE | 无可靠渠道终止证明不宣告关闭/释放；外部稳定请求号与关闭合同成立 |
| D-07 | 渠道已收款、响应或回调ACK丢失 | 一次正常资金记账，异常实收不丢，库存未确认前不履约 |
| D-08 | 同会员两订单同时确认、迟到渠道时间 | 按批准的权威确认规则仅一个首单；零元及全退不重排 |
| D-09 | 两退款并发打满实收与同一组件 | 两层预算都不超额；UNKNOWN不释放；累计免审阈值不被拆单绕过 |
| D-10 | 退款成功/拒绝/过期/重复回调交错 | 已派发不能超时释放，一份账本与终态；保留矛盾资金事实 |
| D-11 | 不可售与可售混合、多次/跨仓退货、回库响应丢失 | 实收数量和可售回库分别守恒；不重复回库，不删除真实验收 |
| D-12 | 发布后标记失败、消费提交后ACK失败、乱序/缺版本 | 至少一次但业务不重复；版本缺口可补查，原事件事实不改写 |
| D-13 | 两Worker抢同任务、进程退出、租约到期旧进程回来 | 只有有效token可提交本地结果；外部调用仍按原业务号恢复 |
| D-14 | 订单与资金事件不同步时读取证据 | 不输出伪同一RR快照；缺前提返回不可用，新协议版本正确 |
| D-15 | 会员冻结/商品下架与建单竞争 | 保持批准的线性化规则；普通缓存/RPC旧结果不能绕过 |
| D-16 | 切库时迟提交记录、延迟消息及旧Worker继续运行 | 单一写入者；永久请求/关闭记录及增量不漏；旧写权限被阻断 |
| D-17 | 其他租户/无权限服务伪造命令和事件 | 在资源绑定前后均阻断，不泄露他租户事实 |
| D-18 | 新库已接写后回退 | 新业务事实完整迁回或保持新权威，不切回旧快照造成重付/超卖 |

P2先完成支付/首单/资格事实含义及消费者审查，P3再解决跨库共同快照及证据版本协议，两个门禁不能混为一项。

P0运行现有机制相关场景，尚无新协议的用例标为“待实现”，不能用单进程Mockito测试冒充多进程验收。P2/P3实现后逐条补齐相应场景。现有基础测试、合同测试和每阶段真实MySQL集成均需继续通过。

报告必须包含：环境和代码指纹、场景/步骤、预期/实际、事件与业务号脱敏关联、故障时间线、断言SQL结果、失败与恢复证据、成功/拒绝/错误数量、P50/P95/P99、队列年龄、连接/锁/CPU/IO。任何超卖、重复资金记账、超额退款或跨租户泄露均失败；吞吐阈值、最长处理中时间和RTO/RPO不在本稿编造。
