# 交易侧对账边界

原合同明确recon-platform负责账单比对，交易侧tc_reconciliation_case保存差异、执行和审计关联。先补交易内部能力，再改造现有recon平台；不在交易中心重复建立第二套发奖或资金真值主库。渠道downloadStatement需要真实渠道时区、结算日、手续费、正负金额、补发更正与完整性合同，当前缺实际渠道合同不能猜测CSV格式或把空下载当成功。

交易内部拟提供：正常和异常收款、成功退款的稳定有界事实导出；可信recon来源差异受理Port及永久来源事件去重；租户内差异查询与有界白名单处置。订单的净消费证据不能替代渠道资金事实：EXCESS等异常收款也必须在对账导出中体现，退款在途与成功分开。数据保留交易时间和本地确认时间，并明确水位；禁止用客户端提供的任意渠道交易号直接标本地成功。

差异表按原tc_reconciliation_case合同落库，但唯一键需包含租户、渠道商户绑定、账单日期、账单稳定行键、修订版本/差异类型，避免同渠道多商户或更正账单被误合并。源报告同时保留不可变证据摘要、来源标识及报告事件键，不能只存可覆盖URL。渠道更正不覆写旧报告；新的比较结果关联原差异形成审计链。只读导出按真实持久流水ID游标而非事件到达顺序，不把多条跨域独立快照称为已对齐的全账本水位。

安全处置候选仅包括触发原支付查单、退款查单、异常收款补偿待审批申请，以及经可信证据确认的人工核对结案。查单仍须原渠道请求号/商户/凭据绑定；金额改变和真实退款走现有领域约束及审批，不能凭后台reason或approvalRef字符串执行。不能暴露任意SQL、覆盖账本、清除everPaid、把UNKNOWN改成功或直接释放退款预占。具体resolve动作在接口/实现前逐一绑定到已有Port和验收规则。

差异请求与处置执行分开：来源报告不是执行授权，运营申请不是资金事实。现有退款审批验证器只绑定退款业务，不能直接复用为通用对账审批证明。需要金额修复且真实审批合同尚未接通时留待审批/待核对状态；可继续完成不改变资金的读取、报告受理和可靠查询调度。

验收保留：跨租户/错商户拒绝，来源永久幂等与同键异内容冲突，长款/短款/金额/手续费/跨日/更正账单，重复调度不重复收付，未知保持不释放，审批/审计/调度失败原子回滚。真实文件完整性、对象存储保留、recon匹配规则和外部平台联调在后续跨项目阶段单独证明，内部Mock不能代替。
