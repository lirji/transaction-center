# 首批实施决策与未覆盖项

## 实际设计落点

1. 同一MySQL数据源，本地事务执行器使用REQUIRED传播，未来订单事务可组合库存服务并统一回滚。通过唯一幂等键加行锁串行化同一命令，事务失败时不留下假成功记录。
2. 库存通过条件UPDATE和数据库CHECK双重保证非负与守恒；余额、不可变操作流水、Outbox同事务。预占只有一个合法终态，既不能确认后释放，也不能释放后确认。该端口没有HTTP入口，未来订单必须提供支付／关单证据后才能调用。
3. 商品公开CatalogPort隔离库存与商品存储；创建入口保留主SKU兼容，另有多SKU管理与服务端报价；草稿只能在非发布状态编辑，每次发布追加快照。会员主体由签名JWT映射，首期不收集手机号、地址或密码，避免未落实加密机制时采集敏感数据。
4. API写请求默认200并返回resourceId；幂等重放返回原资源编号，GET用于读取现状。管理商品版本由请求体expectedVersion传入，当前没有宣称已实现设计总纲中的If-Match／201合同。这些差异在正式V1冻结前必须统一，不让前端猜测。
5. 按用户补充要求，初次将60个持久化操作抽离为9个MyBatis Mapper接口及同名XML；报价、订单和消费事实逐步扩展，支付核心扩展后共17个Mapper／125个SQL操作；Service不再持有JdbcTemplate或SQL，只读模型移入model包。复用同一事务数据源，保留锁、租户及库存条件更新，禁用二级缓存并将一级缓存限定为STATEMENT。具体约束与验收见[持久化分层设计](PERSISTENCE_DESIGN.md)。当前不添加空转发Repository层，后续聚合需要组合持久化操作时再引入有实际职责的适配器。
6. 首期ID采用MySQL自增BIGINT并以字符串输出，不是设计目标中的分布式ID生成器；部署仍限同一数据库cell，跨cell路由与ID策略须在启用多cell前定版。无依据声称已达到三高容量。
7. 迁移V001只创建首批11张业务表，含tc_command和最小tc_outbox；不是完整生产字典的全部表。注册主体暂时与会员同表，后续多身份绑定时以兼容迁移拆成身份表，不能直接删除现有列。

## 本轮复核重点

- 相同注册身份并发只产生一个会员／消费事实／注册事件。
- 幂等冲突不覆盖原请求，重复盘点不二次加库存。
- 多次库存预占组合在外层事务失败时全部回滚。
- 确认与释放竞争仅有一个终态；流水聚合与余额一致。
- 缺少价格或版本不得被JSON默认零值静默接受；JWT接收方与签发方均验证。
- 真实MySQL验证DDL、CHECK、唯一约束、FK、并发与注释；真实RSA/JWKS验证签名，而非仅依赖HTTP测试中的模拟解码器。
