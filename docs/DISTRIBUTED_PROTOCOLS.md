# 交易跨服务协议草案 v1

日期：2026-09-09。状态：设计草案，尚未实现或加入OpenAPI/AsyncAPI；路径、状态和事件名均为候选名。依赖[服务拆分设计](DISTRIBUTED_SERVICE_DESIGN.md)。不改变现有81个HTTP操作、7类V1事件及其消费者合同。

## 1. 公共命令、结果与事件合同

### 1.1 命令信封

| 字段 | 语义 |
| --- | --- |
| protocolVersion | 显式协议版本，不能复用旧V1名称改变语义 |
| tenantId | 正整数文本；从可信身份/路由验证，不能只采信请求体 |
| commandId | 同一业务动作永久稳定；按tenant+调用服务+操作+commandId唯一 |
| correlationId / causationId | 所属流程与直接前序命令/事件，支撑恢复审计 |
| aggregateId | orderNo、reservationGroupNo、refundNo等不可变业务号 |
| expectedVersion / permitEpoch | 条件更新版本或许可代际；两者含义分开，不能混用 |
| payload / requestHash | 规范化业务参数及服务端计算摘要；客户端hash只作提示，不作为可信证据 |
| traceId | 链路观测，不参与幂等与权限裁决 |

金额为币种最小单位整数；ID、版本及超过JavaScript精确范围的整数按合同字符串传递。数量/币种/总额/明细一致性由接收方校验。归属、来源权限及不可变绑定必须在本地事务前后适当位置重检。

命令去重不替代业务唯一约束：资金关闭记录以tenantId+orderNo唯一，库存组状态/取消记录以tenantId+reservationGroupNo唯一，退款申请按永久来源业务引用绑定。换调用者、operation或commandId不能绕过同一业务对象的终止屏障；新的许可代际也不能复活已终止订单。

同键同摘要返回原业务操作及其当前可查询结果；同键不同摘要为冲突，禁止覆盖。受理后不得因HTTP超时换commandId、支付渠道号或退款号。有限HTTP响应缓存可以清理，但财务、预占、归因及关闭业务号的永久唯一约束/终止记录不可随缓存到期删除。

### 1.2 接收与结果

候选HTTP命令为PUT /internal/v1/{operations}/{commandId}，GET同路径查询操作。业务名见后续各节。首次持久受理返回202与operationId、状态、resourceVersion及查询地址；200表示命中已存在操作/可确定结果，不自动表示渠道成功。领域拒绝需有稳定错误码；超时、网络错误及查询不存在不能直接认定此前从未受理。

业务终止后迟到的首次命令仍须被拒绝/返回终态。不存在记录的取消命令也要持久保存关闭或取消标记；只返回404会留下迟到请求重新创建的窗口。

生产方：业务变更+审计+Outbox同一事务；发布器至少一次投递。消费方：Inbox去重+版本裁决+业务变更+后续Outbox/任务同一事务，提交后再ACK。ACK成功丢失会重复投递，不能重复生效。

### 1.3 事件与顺序

事件至少含eventId、eventType、schemaVersion、tenantId、aggregateId、aggregateVersion、occurredAt、correlationId和因果引用；发生时间不当全局顺序。按tenant+aggregate路由分区，发送端维护聚合顺序，但不依赖全局Kafka顺序。

不同消费者维护自己的去重/版本状态。完整状态快照事件可按协议跳过旧版；增量事件缺版本时须等待补齐或查询权威状态，不能直接跳过。跨聚合不能用max(version)合成全局版本。重复、同版本异内容、缺因果引用必须分别处理，冲突保留证据进入核对。

重试需退避、抖动和服务/租户预算；耗尽常规重试后进入持久REVIEW并告警，不丢弃事实。消息过期策略不能清除在途资金责任；各类业务保留期须明确后实施。

## 2. 订单—库存协议

### 2.1 操作与所有权

| 命令/查询候选 | 输入关键字段 | 库存本地裁决与结果 |
| --- | --- | --- |
| ReserveOrderStock | orderNo、reservationGroupNo、warehouseId、items[{skuId,quantity}]、订单冻结摘要 | 同仓多SKU全成或全败；校验调用者有权为此订单预占，锁序固定 |
| ConfirmOrderStock | 原groupNo、订单确认依据/资金事实引用、expectedVersion | RESERVED→CONFIRMED；同结果重放不再扣库存 |
| CancelOrderStock | 原groupNo、订单取消依据或资金关闭引用 | RESERVED→CANCELLED并释放；不存在则写CANCELLED标记；CONFIRMED不能走释放 |
| GetOrderStock | 原groupNo | 返回权威组状态、各项及版本，不以查不到替代取消确认 |
| RestockInspection | 原groupNo、inspectionNo、各项可售数量、目标仓库、可信验收引用 | 校验原确认及累计可回库量，写永久操作、余额和流水同事务 |

库存收到命令需验证订单/验收服务身份、租户和资源绑定，不能只见一个“支付成功”字符串就确认。可通过已经验真的因果事件/本地绑定事实实施，缺前提则等待补齐，不根据字段名放行。

原单仓约束保留。原逐SKU预占号可作为子项，新增groupNo负责整组原子性。库存服务不从商品查询投影重算可售性；冻结商品可售判定由保留在核心的下单事务负责。

### 2.2 建单状态推进

1. 订单事务校验会员、商品、商户、报价时效，永久绑定报价/归因，保存WAIT_STOCK流程及Reserve命令；此时不是已可支付订单。推荐将该事务提交作为本次建单获准的线性化点：后续冻结/下架不回溯撤销已获准的库存建单流程，但新的支付许可仍按当前准入状态检查。这是P2必须签收的时序变化；若业务要求冻结成功时所有未完成建单都终止，则需另加在途流程排空/撤销屏障，未选定前不拆库存。
2. 库存持久处理并输出Reserved或Rejected。订单收到Reserved后再次裁决自身是否仍在可推进的流程；若已取消，则发送Cancel，不能进入待支付。
3. 订单只有取得库存成功事实才开放支付许可。多SKU失败不留下半组预占；订单保留建单失败事实及原幂等结果。
4. 超时只触发查询/恢复，不直接假定预占失败。取消成功对外确认要等库存终止确认；无支付许可且无实物预占可直接终止。
5. Cancel先到、Reserve后到：库存已存在终止标记，迟到Reserve不能重新创建。不同内容重试原groupNo一律冲突。
6. Confirm与Cancel并发：库存同一聚合锁/CAS裁决；合法正常流程不应同时发出两个命令。若出现矛盾依据，保留证据进入核对，CONFIRMED不自动释放；订单必须避免先确认再补发取消。

零元实物订单先预占再确认，确认成功后才可履约；无渠道调用、paidAt为空、NO_PAYMENT_REQUIRED且不写首单事实。纯服务订单不发库存命令。

## 3. 订单—资金协议

### 3.1 不可变订单资金绑定

OpenPayment使用由订单权威提供的orderNo、memberId、merchantNo、currency、payableAmount、明细组件上限摘要和permitEpoch。资金首次受理时建立不可变绑定；重复绑定字段不同即冲突。会员本人请求先由订单验证授权，资金还要验证服务来源及渠道商户配置。

资金持有退款所需的冻结明细，不依赖管理查询投影。异步绑定事件未到时，支付命令可携带相同可信快照以幂等建立；来源验真失败或内容冲突不得调用渠道。

### 3.2 支付许可与关闭屏障

| 命令 | 行为 |
| --- | --- |
| OpenPayment | 请求在原订单许可代际下创建/查询唯一支付意图；不等于渠道已支付 |
| CloseOrderPayment | 持久关闭整个订单支付入口、拒绝后续Open/新attempt；查询并关闭此前全部可能发出的尝试 |
| GetOrderFunding | 查询订单资金状态、原尝试及关闭结果；不允许调用方指定新的渠道交易号 |

一期使用订单级终止屏障：一旦进入关闭流程，该订单不重新开放支付。permitEpoch区分迟到/陈旧命令，不提供关闭后换epoch绕过终止的能力。

- 订单授予许可前先在自身事务保存“可能发生支付”标记和Open命令。此后取消只能进入CLOSING，即使资金尚未见到Open。
- 资金Close先到：即使意图不存在也写订单级关闭记录。迟到Open看到记录后不能建新尝试；记录不能因普通幂等缓存清理而消失。
- Open先到：资金本地事务内串行化计划与Close；计划提交后外部调用可能已经在途。Close必须覆盖所有已授权发出的请求，不能只检查当下没有收款记录。
- 渠道查询超时、NOT_FOUND、连接断开都不构成可靠关闭。若存在进程恢复后可能发送的旧CREATE，必须通过渠道稳定请求号及终止屏障证明该请求再也不能成功；做不到则保持未知并进入核对，不能释放库存。
- 只有资金服务给出不可再正常成功的PaymentClosed事实，订单才发库存Cancel。库存Cancel确认后订单才能完成取消流程。
- 支付成功先于可靠关闭：资金记录成功，Close返回ALREADY_PAID或对应事实；订单继续资金确认后的处理。错误来源导致关闭后出现实收，仍记录异常收款并走受控补偿，不删除资金事实或直接重复履约。

### 3.3 收款与库存确认

资金先耐久接收验真回调，再本地确认正常实收、账本、首次付费事实与Outbox。首付事实在同tenant/member的资金权威内串行裁决，不按事件到达顺序认定。该确认点不同于当前“库存/订单/收款一起提交”，必须在P2提取库存之前批准新策略版本或确认兼容方案，不能等P3才处理。P2权威资金/首单事实仍保留旧交易核心的本地事务，P3才迁移其数据库；远程库存确认不能嵌入MANDATORY充当原子操作。相关支付/首单/零元/证据消费者必须先接受新的中间状态与确认口径。

订单消费收款事实后记录资金已确认，向库存发Confirm；收到库存确认后进入可履约。期间保留独立的财务与执行状态，如FUNDED_WAIT_STOCK_CONFIRM，不把真实收款回滚成未支付。库存暂不可达时重试，永久矛盾进入人工核对/受控退款，禁止直接吞掉成功回调。

订单额度和金额不能以投影覆盖资金权威。一个订单异常多笔实收分别持久记录，但只有一笔正常收款推动正常履约；异常款不推进首单或正常净消费。

## 4. 售后—资金及售后—库存协议

### 4.1 退款受理

RequestRefund输入业务请求号、orderNo、申请人绑定、amount/currency、组件明细、售后证据引用。正常会员申请不允许挑选异常实收；异常补偿使用独立受控操作和原实收唯一关联。

资金事务一次完成：

1. 校验订单/会员/实收与冻结明细可信绑定，不根据异步order.financialStatus裁决额度。
2. 使用永久来源请求号与摘要去重。
3. 对实收总额和各商品项/运费/税组件同时检查“已成功+在途+本次≤上限”。
4. 同事务创建资金hold、组件hold、申请明细、冻结政策/审批要求和恢复事件。任一不足全部回滚。
5. 免审判断按正常实收累计成功+在途+本次，不允许拆单绕过阈值；一期运费/税仍为当前冻结0值，不虚构收费能力。

200/202只表达业务结果或持久受理；不能标注渠道退款成功。售后“同意退款”只是业务依据，不能替代现有trade.refund.approval可信签名回执。签收、防自审自批和来源唯一性继续由资金侧同事务执行。

### 4.2 渠道执行与资金终态

批准后资金形成稳定退款计划，提交后事务外调用。UNKNOWN保留两层额度并查原号；不换号重新退。仅可信成功同时确认两层预算、唯一账本、退款终态与Outbox；仅可靠不可能再成功的失败/合法未派发拒绝释放预算。补偿失败写入持久恢复/REVIEW并告警。

订单的退款展示/财务状态通过事件收敛；资金证据已变化而订单尚未更新期间不能用旧订单字段发奖或再次授权退款。此差异必须由新的证据协议明确，不能保持旧evidenceVersion假象。

### 4.3 退货验收和回库

售后在本地事务核验真实交付、原订单项、累计实收预算，记录验收和Restock命令。不可售数量仍消耗实收预算，但不增加可售库存；退款数量与退货数量互不替代。

库存以inspectionNo+原预占/明细唯一执行，并独立检查原确认数量与累计可售回库预算；目标仓与原仓关联、余额和流水在库存库同事务裁决。响应丢失后查原操作，不重复加库存。

售后已记录真实收货但库存处理失败时，保留验收事实并显示RESTOCK_PENDING/REVIEW；不得为“全局回滚”删验收或重新生成inspectionNo。原“验收和回库同事务成功”的外部响应及ETag含义需版本化，不能沿用旧成功码让调用方误判已回库。

## 5. 故障与恢复矩阵

| 故障/竞争 | 持久事实 | 恢复与终止依据 |
| --- | --- | --- |
| 本地提交前进程退出 | 没有业务与Outbox提交 | 原命令可重试；接收方按唯一键裁决 |
| 提交后发消息前退出 | 业务与Outbox均存在 | 发布Worker继续投递 |
| Kafka已收但本地未标记发布完成 | 消息可能已投递 | 重投同eventId，消费Inbox去重 |
| 消费业务提交后ACK丢失 | Inbox与业务同时存在 | 重投只返回已处理，不再加预算 |
| 库存Cancel先到Reserve后到 | 原group终止标记 | 迟到Reserve不能复活 |
| 支付Close先到Open后到 | 原order终止屏障 | 迟到支付命令不能创建新尝试 |
| 渠道调用超时/旧Worker稍后恢复 | 原渠道请求可能生效 | 查原号/可靠终止协议；无证明不得释放 |
| 成功资金事实到达但订单不可用 | 收款、账本、Outbox存在 | 订单恢复后确认库存，财务事实不丢 |
| 消费事件乱序/缺版本 | Inbox与最后应用版本 | 补齐缺口或查询权威，不能盲增退款/库存 |
| 退款成功与取消申请竞争 | 资金同事务版本/派发状态 | 已派发或未知不能按审批超时释放 |
| 已验收但回库未成功 | 验收与库存操作号存在 | 原号重试/查询，失败保留待处理 |
| 协调者租约过期、旧实例继续写 | 流程版本和fencing token | 本地陈旧提交拒绝；远程命令仍靠业务幂等/终止屏障 |
| 同key不同payload | 永久业务绑定/摘要 | 返回冲突并留审计，不能覆盖原请求 |
| 系统长时不可用 | 恢复任务、资金/资源责任仍存在 | 告警、核对和恢复；不以重试耗尽自动判失败 |

## 6. 查询合同与容量边界

P1须按页面字段与源表列出新增/修改/删除或终止状态的覆盖矩阵；现有7类V1事件不自动覆盖未支付订单、报价、支付尝试、异常实收、退货及任务租约等全部页面。缺事件则补经评审的版本化快照/变更事件，或受控CDC和水位；无法重建的页面先保留权威查询。

普通管理列表可以使用独立读模型，显示每域版本/observedAt，允许部分面板单独失败；不提供伪全局快照时间。命令完成后需要强读时路由权威服务或等待明确版本，有界等待超时返回处理中。

订单证据、营销资格和财务对账不是普通列表：旧RR合同继续有效直到新版本正式替换。聚合等待因果前提可返回EVIDENCE_UNAVAILABLE，不能缺资金字段就填零。消息投影不能自动等价于原营销资格裁决。

尚未确定的参数包括并发、超时、可接受传播延迟、告警年龄、恢复时限和消息保留期；须通过隔离实验与业务SLO确定，不从本机默认线程数推导生产承诺。全链路不能在前端、网关、服务、Worker各自无预算叠加重试。
