# 退款原路渠道与恢复接续

## 当前交付和原要求

沿用FINAL_PLAN 6.4、TC21/22/25及REFUND_IMPLEMENTATION_PLAN阶段3；不是缩小完整退款范围。本切片新增RefundChannelPort/Adapter/Service、RefundEvidencePort和VerifiedRefundEvidence，仅提供渠道调用与证据交接边界。无新增HTTP、DDL或真实供应商实现；共享库保持V014。

渠道策略注册表按固定channelCode选择实现，重复代码或重复证据接收器启动失败。没有适配器或持久化接收器返回UNAVAILABLE，禁止先发网络再发现无法保存结果。暂不配置默认模拟成功实现。

## 调用边界

1. Worker在数据库事务中取得当前退款执行计划，提交派发屏障与最后fencing。
2. 事务外调用RefundChannelPort.invoke；显式拒绝活动事务、跨租户、非CREATE/QUERY、无效绑定和金额。
3. Adapter只能使用同一计划中的原商户、原扣款号、退款号、金额及币种。不得换号、换渠道。
4. 断连/超时返回UNKNOWN；普通查不到为PENDING/UNKNOWN。二者不能确认失败、释放额度或启用新号。
5. EVIDENCE要求服务端完成验签或认证查询；同渠道/商户/退款号交给RefundEvidencePort持久接收。异常金额/币种/原扣款号保留，后续核对，不能丢弃真实资金。
6. 接收器提交失败必须抛异常，不返回EVIDENCE_ACCEPTED。正常返回只表示持久接收，不表示业务退款已经确认。

退款渠道失败终态必须证明原号永久不可再成功；不能由普通HTTP200、404、过期或管理员指令推断。当前Reply不提供无证据SUCCESS/FAILED布尔值，也不提供自动换号或查不到就重建路径。

十秒只是传给Adapter的预算，不代表本服务已强制实施整体网络超时。具体连接/读取/整体超时、限额、熔断、验签、永久幂等及可安全同号重放合同仍须真实适配器逐项认证。尚未发出的CREATE在派发屏障后崩溃，需后续受认证同号重放能力恢复；不能永久以查询代替这项可用性要求。

## 持久Inbox下一切片设计

当前实现更新：下述接收/认证/租约处理已落实为RefundInboxService、RefundCallbackWorker与V015，具体边界和验证见[退款回调Inbox](REFUND_CALLBACK_INBOX.md)。核心EvidenceProtectionPort由服务装配层复用现有公开加密Port，没有让refund引用payment实现。REFUND_CALLBACK已注册第四通道，REFUND_RECOVER仍待继续。共享执行状态以最新进度为准。

新增V015，禁止改V001～V014。RefundMapper仍只访问退款所属表，新增专用RefundInboxMapper/XML。证据表必须有中文表/字段注释，含租户/内部接收号/退款绑定/渠道商户事件永久唯一键、解析事实、原文摘要、事实摘要、密文/密钥版本/签名版本、接收及处理状态与时间、核对错误分类。

接收顺序：可信适配器→校验格式和请求归属→加密必要原文→短事务插入/唯一键当前读/冲突检测→同事务入队REFUND_CALLBACK。独立提交，不以旧Worker租约判断是否应该保存已到达的资金证据。不能先应答再落库，不能同事件不同事实静默覆盖。

处理顺序：持租约读证据→校验密文AAD/摘要→锁订单/支付意图/实收/hold/申请/组件→可信成功或失败处理→处理标记→末尾fencing同事务提交。金额/币种/原扣款号不一致或已释放后的矛盾成功保留证据并转受控REVIEW，不能删除或伪装成功。退款后everPaid不变、库存不自动增加。

需要补充按merchantRefundNo读取不可变归属的退款内部方法，避免Inbox跨域访问支付Mapper。原渠道凭据仍由支付域不可变渠道配置提供，退款不能自行重选商户。密文保护应通过核心公共Port复用安全基础能力，不跨域引用payment实现。

Worker新增REFUND_RECOVER和REFUND_CALLBACK，覆盖审批到期、READY派发、SUBMITTED查询、同号安全重放、成功/可靠失败/人工核对。纳入现有有界运行时/租户发现/任务补漏，不另开无租约定时旁路。

## 验收门禁

### 主动恢复实施入口（V016源码已实现，真实渠道认证仍待完成）

最新实现为RefundRecoveryWorker及RefundRecoveryBackfillService，详见[主动恢复合同](REFUND_RECOVERY_WORKER.md)。本节保留实施依据；上文V015的“REFUND_RECOVER仍待继续”为历史阶段状态。验证与共享迁移以最新CODEX_PROGRESS及原始报告为准。原路凭据公开Port仍待实现，不能把现有策略边界当作真实渠道已经接通。

复用PaymentRecoveryWorker的“许可与fencing提交→事务外渠道→独立耐久接收→退避”结构，但退款审批和资金终态不能套用支付取消/库存释放规则。新增RefundRecoveryPort及jobs/RefundRecoveryWorker，返回内部执行计划与待审批重检时间；WAIT_APPROVAL只安排唤醒，不派发。达到冻结approvalDeadline后调用expireApproval，与jobs.complete同事务；审批决定与到期竞争仍以订单锁及当前申请状态裁决。

申请创建时同事务预约REFUND_RECOVER；批准/拒绝时使用持久wake，不能只发内存事件。成功或可靠失败的持久回调处理后唤醒主动恢复任务，使其确认本地终态并结束。V016增量扩展任务白名单，初始化已有非终态申请任务；另提供租户/主键有界补漏服务，旧写入退出后从零收尾，不用一次全表长事务替代滚动升级。

已提交派发屏障但尚未发网时宕机，后续默认QUERY不能证明不存在。扩展Adapter显式认证的原号永久幂等/同参数重放能力，只有认证QUERY返回可安全补建证明时，Worker重新读取本地退款状态、复核批准依据及原资金绑定、末尾fencing，然后按同一退款号CREATE。每次租约最多一次补建；普通404、UNKNOWN或没有认证能力不得触发。真实渠道认证仍是上线前置，不能以本地布尔开关宣称完成供应商验收。

原渠道凭据需经支付公开Port按不可变paymentAttemptId解析原配置引用，不把密钥加入日志、HTTP或退款Mapper。多付补偿仍使用其独立实收来源；本轮正常退款申请不能代替补偿应用。长期UNKNOWN/异常证据进入受控核对与告警，不因重试次数清空预占。

运行时新增第五独立通道并重新核算总槽位/连接池/渠道预算；默认仍关闭。测试须覆盖审批和过期交错、派发前宕机、网络已执行但应答丢失、同号补建、查询/回调竞态、旧租约、持久唤醒不丢、滚动补漏及隔离停机。现有13项退款Inbox测试不能替代这些主动恢复案例。
