# 历史发布补漏与持久队列观测

Worker 的 `TRADE_OUTBOX_MAINTENANCE_ENABLED=true` 显式启用历史补漏；默认关闭，API 角色强制关闭。维护无需打开 Kafka 发布开关。每个进程仅一个维护线程，每 tick 默认 200ms 最多处理一个租户的一页（默认 100 条）。单页 RC 事务超时 5 秒，入队和持久游标一起提交；失败从原页重试。

每租户保存固定 upper ID 的有限轮次，轮次完成后默认等待 5 分钟再从 0 扫描。已经提交的最大 ID 不是提交水位，后续轮次会再次发现迟提交的低 ID。只处理 PENDING 且属于 V1 发布目录的事件，已有 DONE/REVIEW 任务不会被补漏重新激活。候选计数表示观察到的候选，不能当成实际新增任务数。

## 抓取与告警

Worker 默认每 15 秒独立采样 OUTBOX_PUBLISH 的 READY/RUNNING/REVIEW 队列。每状态扫描索引前 10001 条，计数是下界；10001 表示至少 10001 条。最老年龄从任务首次创建计算，包含人工重放前的历史，并非本轮重放耗时。采样单条 SQL 使用覆盖索引；指标抓取仅读缓存，不访问数据库。

`GET /actuator/prometheus` 要求可信 JWT 且拥有 `trade.metrics.read`。配置抓取任务标签 `job="transaction-center-worker"`，使用已有可信认证体系签发并轮换抓取令牌。普通 `trade.admin` 无此权限。API 进程不采样队列。

规则文件为 `deploy/monitoring/outbox-alerts.yml`。同一数据库多个 Worker 观察的是相同全局队列，规则先按 job/instance 排除超过 60 秒的旧样本再使用 max，不能 sum；每个实例独立判断观测过期，避免健康实例掩盖故障实例。每个独立环境的 Prometheus 使用独立规则评估；多数据库聚合时需按数据库部署标签分组调整规则，不能让健康库掩盖另一库。

首次采样失败时计数为 NaN、采样时间为 0；后续失败保留旧样本并增加故障计数。必须同时加载观测过期与缺失告警，不能单凭积压指标没有报警判断队列为空。阈值是初始运营配置，需要结合目标发布时延调整。当前规则文件尚未代表已接入 Alertmanager 或已向外部工单/人员投递。

## 处理路径

1. 收到 REVIEW 告警后，通过有租户授权的 Outbox 后台查询定位事件或坏键摘要；监控标签不包含租户、事件、载荷或工单。
2. 修复原因后使用受控重放接口，提供幂等键、版本、原因和工单引用，且同时具备 `trade.admin` 与 `trade.events.replay`。引用不等于系统已创建外部工单。
3. 对发布延迟先检查发布开关、Kafka 连接和 ACK、租约状态；禁止通过重置全局 attempts、修改原 eventId/payload 或把 REVIEW 强改 READY 绕过凭证。
4. 对观测过期/缺失检查 Worker、数据库及抓取鉴权。维护页错误只重试持久游标，不修改资金或直接发送事件。

停止维护只关闭发现并有界排空当前事务；再启动保留数据库轮次。V024 在阶段验证与审查通过后方可执行共享库迁移；测试库迁移不等于共享库或生产部署完成。
